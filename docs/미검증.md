# 미검증 항목 목록

하드웨어(카메라, 라즈베리파이, 아두이노 UNO)가 없어 **Windows 로컬 환경에서 검증하지 못한 항목**과 확인 방법을 모은다.
설계서(`docs/설계서.docx`)의 각 단계 "미검증 항목" 절과 같은 내용을 한곳에 정리한 것이며, 확인하면 상태를 바꾸고 결과를 적는다.

- 마지막 갱신: 2026-10-15 (파이 로케일·브로커 확인)
- 상태: ⬜ 미검증 / ✅ 확인함 / ❌ 문제 있음
- 로컬에서 대신 확인한 방법은 "대체 검증" 열에 적었다.

## 0. 공통 — 환경

| 상태 | 항목 | 대체 검증 | 확인 방법 |
|---|---|---|---|
| ✅ | 파이 OS 결정 (Bookworm 가정, Python 3.11) | 없음 | `cat /etc/os-release`, `uname -m` → **Bookworm, aarch64 확인 (2026-10-14)**. 가정과 같아 requirements 변경 없음 |
| ✅ | 파이에 requirements-pi.txt 설치 (apt + venv `--system-site-packages`) | Windows venv | 설치 후 `python -c "import cv2, pyzbar, paho.mqtt, serial; print(cv2.barcode)"`. **2026-10-14 확인**: 설치 성공. 당시 로케일이 UTF-8이 아니어서 `PYTHONUTF8=1`로 설치 (2026-10-15 로케일 변경으로 해결, 아래 항목). 처음에 `cv2.barcode`가 False → 진단·재설치 후 True |
| ✅ | Bookworm apt picamera2와 venv의 numpy<2 공존 | 없음 | `python -c "import picamera2, numpy; print(numpy.__version__)"`. **2026-10-14 확인**: picamera2 import 정상, numpy 1.x |
| ✅ | 파이 시스템 로케일 UTF-8 (systemd 서비스는 셸 설정을 읽지 않음) | 없음 | `sudo update-locale LANG=en_US.UTF-8` 후 재부팅, `locale`, `env -u PYTHONUTF8 python -c "import locale; print(locale.getpreferredencoding())"`, `env -u PYTHONUTF8 pip install -r requirements-pi.txt --dry-run`. **2026-10-15 확인**: 모두 정상 (UTF-8, 인코딩 오류 없음) |

## 1단계 — 바코드 인식 → MQTT 발행

| 상태 | 항목 | 대체 검증 | 확인 방법 |
|---|---|---|---|
| ⬜ | Pi 카메라 모듈로 실물 바코드 인식 (초점·조명·거리) | 합성 이미지 (`--camera files`) | `python -m barcode_system.scanner_app --config config/scanner.ini --show --debug`, 상품 EAN-13·인쇄한 Code128을 거리별로 비춤 |
| ⬜ | Pi 카메라 모듈 3 연속 오토포커스 동작 | 없음 | 로그에 "연속 오토포커스 활성화", 10cm 이내 바코드 인식 |
| 🔄 | USB 웹캠 (Windows DirectShow / 파이 V4L2) | 백엔드 선택 로직 단위 테스트 | `--camera usb --show`, 로그의 실제 해상도 확인. Windows에서 느리면 `--backend msmf` 비교. **2026-10-16 Windows 확인**: 학교 PC + `HD 4MP WEBCAM`(PCWE400)로 CODE128 인식·발행 성공(`--show true`). 흐릴 때 EAN 잘못 읽음 있음. 파이 V4L2는 미사용 |
| ⬜ | 파이에서의 처리 속도(FPS)·CPU 사용률 (OpenCV+ZBar 동시 실행) | 없음 | `top`, 느리면 `--engine zbar` 또는 해상도 낮춤 |
| ⬜ | 카메라 USB 분리 → 자동 재연결 | 없음 (코드 경로만) | 실행 중 웹캠 USB를 뽑았다 꽂기, 로그 "카메라 재연결 성공" |
| ⬜ | UPC-E, I25, Codabar, DataBar 인식 | 없음 (생성기 없음) | 해당 바코드 실물 또는 인쇄물로 확인 |
| ✅ | 실제 Wi-Fi 단절·복구 시 outbox 전송 | TCP 프록시로 연결 차단 (test_publisher) | 스캐너 파이의 Wi-Fi를 끄고 스캔 → 켠 뒤 `db_tool gaps`가 비어 있는지. **2026-10-16 확인** (스캐너는 Windows PC): 핫스팟 끊은 동안 2건 → 재연결 시 전송·저장, `gaps` 없음 |
| ⬜ | 스캐너 파이 전원 차단 후 outbox 보존 | 프로세스 강제 종료 (test_scanner_app) | 스캔 직후 전원 차단 → 재부팅 후 전송·`gaps` 확인 |
| ✅ | 파이 Mosquitto 설치 스크립트 `mosquitto/pi/setup_broker.sh` | Windows Mosquitto 2.1.2에 같은 ACL | `sudo mosquitto/pi/setup_broker.sh dock-01 db-writer uno-bridge monitor`. **2026-10-15 확인**: 패키지는 이미 설치·실행 중이었고 설정 3개(barcode.conf, acl, passwd)가 없어 스크립트로 설치 → 설정 파일이 프로젝트와 같음, 사용자 3명 등록, 1883 리스닝 |
| ⬜ | NTP 동기화 전 스캔의 시각 | 없음 | 부팅 직후 스캔 → DB의 `scan_ts`와 `received_at` 비교 |

|---|---|---|---|
| 🔄 | systemd 서비스 설치·부팅 자동 실행·비정상 종료 시 재시작 | 없음 | `sudo deploy/install_services.sh db-writer`, `sudo kill -9 <pid>` 후 3초 뒤 재시작되는지 `journalctl -u barcode-db-writer`. **2026-10-16**: 설치·재부팅 후 자동 실행(mosquitto·db-writer active)·스캔 저장 확인. `kill -9` 재시작은 아직 |
| ✅ | 파이 OS의 Mosquitto 버전(Bookworm 2.0.11)에서 설정 호환 (`autosave_on_changes`, `persistent_client_expiration`) | Windows Mosquitto 2.1.2 | `sudo systemctl restart mosquitto` 후 `journalctl -u mosquitto`에 설정 오류가 없는지. **2026-10-15 확인**: 설정을 읽고 정상 기동, monitor 구독·dock-01 발행 수신, 익명 접속 거부 확인 |
| ⬜ | SD카드에서 브로커 저장(변경마다) 부하·DB 쓰기 성능 | 없음 | 초당 수 건 스캔을 1시간 유지, `iostat`/`vmstat` 확인 |
| ⬜ | 실제 전원 차단 후 db-writer·브로커 복구 | 프로세스 강제 종료·브로커 kill (test_pipeline) | db-writer 정지 상태에서 스캔 → 파이 전원 차단 → 재부팅 후 DB 반영 확인 |

## 3단계 — 아두이노 UNO 연동

| 상태 | 항목 | 대체 검증 | 확인 방법 |
|---|---|---|---|
| ⬜ | CH340/CH341 호환보드에 스케치 업로드 | `arduino-cli compile` 성공 (Flash 30%, SRAM 35%) | `arduino-cli upload --profile uno -p <포트> arduino/uno_display` (README 참조) |
| ⬜ | Windows CH340/CH341 드라이버 | 없음 | 장치 관리자에 `USB-SERIAL CH340 (COMx)` 표시. 없으면 WCH CH341SER 설치 |
| ⬜ | 포트 자동 검색(`port = auto`)이 실제 보드를 찾는지 (VID:PID 1A86:7523 / 1A86:5523) | 가짜 포트 목록 단위 테스트 | `python -c "from barcode_system.serial_bridge import find_port; print(find_port())"` |
| ⬜ | 포트를 열 때 UNO 리셋 → R 수신 (CH340 보드의 DTR 리셋) | 가짜 UNO | 브리지 로그 "UNO 연결됨: ... (펌웨어 uno-display/1)". "확인 안 됨"이면 리셋 회로 없는 보드 |
| ⬜ | 115200bps 통신 오류율 | 가짜 UNO (TCP) | 브리지 로그에 "확인 없음 → 재전송"·`E|CK`가 자주 나오면 `SERIAL_BAUD`·`baud`를 57600으로 함께 낮춤 |
| ⬜ | I2C LCD 주소(0x27/0x3F) 자동 검색·표시 | 없음 | 전원 인가 시 `Barcode Display / waiting...` 표시. 안 보이면 명암 가변저항 조정 |
| ⬜ | LED·부저 배선과 부저 종류(능동/수동) | 없음 | 부팅 시 LED 2개 0.2초 점등, 저장 시 짧은 삐. 소리가 이상하면 `BUZZER_PASSIVE` 변경 |
| ⬜ | 저장/거부/lost/NO LINK 표시가 의도대로 보이는지 | 프로토콜·브리지 동작만 (가짜 UNO) | README의 "단독 시험"으로 각 프레임 전송, 또는 전체 시스템에서 스캐너 정지(lost)·브리지 정지(NO LINK) |
| ⬜ | USB 케이블 분리 → 재연결 | 가짜 UNO unplug/plug | 실행 중 UNO USB를 뽑았다 꽂기 → 로그 "UNO 연결됨", 스캐너 상태 다시 표시 |
| ⬜ | 파이에서 `dialout` 권한으로 시리얼 접근 (systemd) | 없음 | `sudo deploy/install_services.sh uno-bridge`, `journalctl -u barcode-uno-bridge` |
| ⬜ | UNO 장시간 동작 (millis 넘김 49일, SRAM 단편화) | 코드 검토 (넘김에 안전한 비교, 동적 할당은 부팅 때 1회) | 장기 운영 중 관찰 |

## 4단계 — 대시보드 전송

| 상태 | 항목 | 대체 검증 | 확인 방법 |
|---|---|---|---|
| ✅ | 실제 대시보드에 POST (`Apple123`, `pants2` 각 1건) → 재고 +1·이력 1건 | 가짜 서버 (`tests/test_forwarder.py`, 25개) | 파이에서 forwarder 실행 → PC에서 스캔 → 로그 `전송 ... transactionId=...`, 대시보드에서 재고·이력 확인. `--status`로 완료 건수 확인. **2026-10-16 확인**: Apple123 재고 1, pants2 재고 2(두 번 스캔), 이력 수와 일치 |
| ✅ | Cloudflare를 통과하는지 (urllib 기본 User-Agent는 403 Error 1010) | 없음 | **2026-10-16 PC에서 확인**: User-Agent `barcode-forwarder/1.0`으로 GET 이력 조회 성공. 파이에서 POST도 통과 (2026-10-16) |
| ✅ | 파이에서 읽기 전용으로 barcodes.db를 붙여(ATTACH) 조회 (db-writer 실행 중) | Windows에서 ScanStore를 연 채로 조회 | forwarder 실행 중 새 스캔이 바로 전송되는지 |
| ✅ | 인터넷 끊김(아이폰 셀룰러 데이터 끔) → 복구 후 재전송, 재고 중복 없음 (2026-10-16) | 가짜 서버 장애(503·연결 끊김·시간 초과) | 핫스팟을 끈 채 스캔 → 켠 뒤 대시보드 재고가 스캔 수와 같은지 |
| ✅ | systemd `barcode-forwarder` 설치·부팅 자동 실행 (2026-10-16) | 없음 | `sudo bash deploy/install_services.sh forwarder`, 재부팅 후 `systemctl is-active barcode-forwarder` |
